CHANGE:
  Package payment capture (§6) plugin-side code, and the full
  Replacement Session / credit flow (§11) — the two pieces that
  were flagged as entirely unbuilt in the last progress review.

  Payment (WPES_Payments, new):
  - maybe_capture_package_payment( $order, $session_id ) — the
    single trigger point. Deliberately calls no gateway-specific
    API: it only transitions the WooCommerce order to 'completed'
    when (and only when) that order is currently 'on-hold' and not
    already captured. This is not a guess — I pulled the actual
    installed WooPayments plugin source from staging via FTP and
    confirmed directly in its code that it binds its own capture
    logic (capture_authorization_on_order_status_change) to the
    core `woocommerce_order_status_completed` hook, and that its
    "Capture charge" admin button is just the standard WooCommerce
    order-action hook `woocommerce_order_action_capture_charge`.
    Using the order's own status lifecycle rather than either of
    those directly keeps this genuinely gateway-agnostic, matching
    the spec's explicit "no custom payment system" requirement.
  - IMPORTANT — this code is currently INERT. It guards on the
    order status being 'on-hold', which never happens until
    WooPayments' "manual capture" setting is turned on (currently
    OFF on staging — confirmed via the WooCommerce REST API). That
    is a gateway-level configuration change, not plugin code, and
    the developer/AI-assistant paused on making it without the
    client's explicit go-ahead, consistent with "contact us before
    changes involving payments." Nothing else in this entry depends
    on it being on.
  - Verified while investigating: WooPayments' own settings screen
    states the authorization must be captured within 7 days or it
    is automatically cancelled. This is the concrete answer to the
    spec's own requirement to verify the gateway's supported
    pre-authorization period — worth the client/dev team confirming
    packages realistically fill within that window.

  Replacement Session (WPES_Replacements, new):
  - New table wpes_replacement_credits (one row per credit: source
    booking/session, customer, status, and where it was redeemed).
  - process_session_failure( $session ) — called from the existing
    final-check cron once a session is confirmed to still be below
    minimum this close to starting: cancels the session, cancels
    every confirmed booking on it, issues one credit per booking,
    emails each affected customer.
  - redeem_credit() — reuses the exact same WPES_Bookings::reserve()
    + confirm() path a paying customer goes through (so capacity
    and race-safety come for free), just without a checkout, so no
    additional charge is ever created.
  - My Account (My Sessions) now shows any available replacement
    credit with a session dropdown and a plain-POST "Confirm
    Replacement Session" button (admin-post.php, nonce-protected,
    no new JS) — redeeming redirects back with a plain-language
    success/failure notice.
  - WPES_Teacher_Invites::run_final_checks() now actually acts on
    the failure case instead of only ever re-inviting — this closes
    the gap flagged in the last progress review, where a session
    that never reached its minimum just sat there indefinitely.

  Also refactored the "session just confirmed" side effects
  (confirmation email, auto meeting-link send, and now payment
  capture) out of handle_accept() into a shared
  finalize_session_confirmation(), and wired the same call into the
  manual admin-assignment path (WPES_Admin::ajax_update_session) —
  previously an admin manually assigning a teacher got NONE of
  those side effects, only the automatic Accept-Link path did.
  Fixed for consistency; only fires on a genuine new assignment,
  not on every session re-save.

  replacement bullets, and the Overview PDF's red path (Minimum
  NOT Reached -> Replacement Session).

CHANGE:
  Client review flagged four areas for correction before final
  acceptance: the minimum-participant check at the final confirmation
  stage, payment-capture safety, replacement-credit concurrency, and
  protection against duplicate teacher invitation rounds. The client's
  message named the four areas but not specific bugs, so each was
  audited directly against the running code; all four turned out to
  be genuine gaps, now fixed. Bumped DB_VERSION 1.7.0 -> 1.8.0 and
  WPES_VERSION 1.7.1 -> 1.8.0 (one new table).

  1) Minimum-participant check at final confirmation
     (WPES_Teacher_Invites::handle_accept()):
     Previously, a teacher's Accept-Link click only re-checked that no
     teacher was already assigned — it never re-checked that the
     session still met the minimum participant count at that exact
     moment. A cancellation/refund between the invite being sent and
     the teacher clicking (up to teacher_invite_hours later, default
     4h) could let a session confirm below minimum. Fixed by folding
     a live COUNT(*) of confirmed bookings into the same conditional
     UPDATE that claims the assignment, so both checks are atomic
     together. Added a new outcome, 'minimum_no_longer_met', with its
     own message on the public Accept-Link page
     (public/class-wpes-public.php) so a teacher who clicks after
     that point sees an accurate reason instead of a generic "already
     assigned".

  2) Payment-capture safety (WPES_Payments::maybe_capture_package_
     payment()):
     Previously guarded only by reading order meta and order status —
     a plain read with no atomicity. A package with several sessions
     can have more than one reach "confirmed" within milliseconds of
     each other (two Accept-Link clicks landing back-to-back, or a
     cron sweep overlapping a manual admin assignment), and every
     confirmation on the order calls this method — nothing stopped
     two concurrent calls both seeing "not yet captured" and both
     proceeding. Fixed with a new table, wpes_payment_captures, whose
     UNIQUE KEY on order_id makes the claim atomic via INSERT IGNORE:
     only the first of any concurrent callers for a given order can
     ever win it. Storage-agnostic by design (works the same under
     HPOS or legacy postmeta, since it's the plugin's own table, not
     WooCommerce's order storage).

  3) Replacement-credit concurrency (WPES_Replacements::redeem_
     credit()):
     Previously a textbook check-then-act race: the credit's status
     was read and checked ('available'), and only much later —
     after reserving and confirming an entirely new booking — was it
     written back to 'used', with no condition on the WHERE clause.
     Two near-simultaneous redemption attempts for the same credit (a
     double-click, two open tabs) could both pass the initial check
     and each create their own booking, double-spending one credit
     into two sessions. Fixed by claiming the credit FIRST, via a
     single conditional UPDATE ... WHERE status = 'available' — only
     the caller that wins it proceeds to reserve a booking. If the
     reservation itself then fails (session filled up in the
     meantime), the credit is handed back to 'available' rather than
     being burned on a redemption that never happened.

  4) Duplicate teacher invitation rounds
     (WPES_Teacher_Invites::maybe_invite_teachers()):
     Previously guarded only by has_pending_invites(), a plain SELECT
     COUNT checked before inserting new invite rows — another
     check-then-act race. Two bookings confirming within milliseconds
     of each other, both pushing the same session past its minimum,
     could both pass that check before either had inserted a row, and
     each send a full duplicate round of invites to every suitable
     teacher (duplicate emails, duplicate DB rows). Fixed by wrapping
     the check-and-insert in a transaction with SELECT ... FOR UPDATE
     on the session row — the same locking discipline AGENTS.md
     requires of any new path touching this row
     (WPES_Bookings::reserve()). Invite emails (external I/O) are
     still sent only after the transaction commits, so the lock is
     never held across a network call.

  All four fixes follow the same compare-and-set/row-lock discipline
  already established elsewhere in this plugin (WPES_Bookings::
  reserve(), the original WPES_Teacher_Invites::handle_accept())
  rather than introducing a new pattern.

REASON:
  Direct client feedback after reviewing the current staging build
  and change log, ahead of final acceptance. Matches Developer
  Specification §5/§14's "even with almost simultaneous ... requests"
  requirement and §6/§9's minimum-participant and payment-safety
  requirements — these are hardening fixes to already-implemented
  features, not new functionality.

    class-wpes-payments.php recording this verification for future

  VERIFICATION — Point 2 (capture exactly once per package):
  - Traced the full call path: every session's confirmation (via
    either the automatic Accept-Link or a manual admin assignment)
    goes through WPES_Teacher_Invites::finalize_session_confirmation(),
    which collects the distinct order_id(s) behind that session's
    confirmed bookings and calls maybe_capture_package_payment() once
    per order — this already happens once per *session*, by design,
    so a multi-session package naturally calls it multiple times
    across its lifetime (once per session as each confirms).
  - What stops a second (or third, fourth, ...) call from actually
    capturing again: maybe_capture_package_payment() checks
    CAPTURED_META first — once 'yes', every later call for that order
    returns false immediately, before touching anything else. This
    fast path alone covers the ordinary "one session confirms after
    another" case for any number of sessions in the package.
  - What stops two sessions confirming close enough together that the
    meta read/write itself could race (the exact scenario fixed in
    the 2026-09-07 16:00 UTC entry): the wpes_payment_captures table's
    UNIQUE KEY on order_id, claimed via INSERT IGNORE — only the
    first of any concurrent callers can ever win it, regardless of
    how many sessions or how close together they confirm.
  - Together, these two mechanisms guarantee exactly one capture per
    order no matter how many sessions the package has or in what
    order/timing they confirm — directly satisfying "subsequent
    confirmed sessions belonging to the same package must not trigger
    another capture."

    this reasoning at the source.

  THE BUG:
  With manual capture enabled, every new order lands on 'on-hold'
  (authorized, not yet captured) at checkout — this is normal,
  expected gateway behaviour. WPES_WooCommerce::mark_bookings_on_hold_
  for_order() (pre-existing, originally built for offline/bank-transfer
  on-hold orders) marks that order's bookings with booking status
  'on-hold' — a status distinct from 'confirmed'. But:
  - WPES_Teacher_Invites::count_confirmed_attendees() — the function
    every minimum-participant check in the plugin calls — only ever
    counted status = 'confirmed'. 'on-hold' bookings never counted
    toward the minimum.
  - Nothing ever called maybe_invite_teachers() when an order went
    on-hold — that call only happened from confirm_bookings_for_order(),
    which is hooked to woocommerce_order_status_processing/completed,
    never to on-hold.
  Together: an on-hold order's bookings could NEVER push a session to
  its minimum, so the invite -> teacher-assignment -> confirmation ->
  capture chain could never start on its own, so the order would sit
  on-hold indefinitely (until WooPayments' own 7-day auto-cancel).
  With every single new order landing on-hold once manual capture is
  on, this would have silently broken the minimum-participant/
  teacher-assignment/payment-capture pipeline for the entire site the
  moment the client turned this setting on for real use — a complete
  deadlock, not a partial degradation.

  THE FIX (five call sites, one consistent rule: 'on-hold' bookings
  count as genuinely reserved, the same as 'confirmed', for every
  purpose except the customer-facing "has this order's payment
  settled" question):
  1. WPES_Teacher_Invites::count_confirmed_attendees() — now counts
     status IN ('confirmed','on-hold').
  2. WPES_Teacher_Invites::handle_accept()'s atomic UPDATE — the
     correlated subquery re-check now uses the same IN ('confirmed',
     'on-hold') condition.
  3. WPES_WooCommerce::mark_bookings_on_hold_for_order() — now also
     loops the order's line items and calls maybe_invite_teachers() per
     session, mirroring confirm_bookings_for_order()'s existing pattern
     exactly. This is the piece that actually starts the chain.
  4. WPES_Teacher_Invites::finalize_session_confirmation() — now
     promotes that specific session's 'on-hold' bookings to 'confirmed'
     via a new WPES_Bookings::confirm_on_hold_by_session() the moment
     the session is genuinely confirmed (scoped to that one session
     only — other sessions in the same multi-session package stay
     'on-hold' until they individually reach their own minimum, per
     Developer Spec §8's independent-session-processing requirement).
     Its capture-order-lookup and WPES_Emailer::send_session_confirmed_
     to_attendees() now both include 'on-hold' bookings too.
  5. WPES_Replacements::process_session_failure() — now cancels and
     issues a replacement credit for 'on-hold' bookings on a failed
     session too, not just 'confirmed' ones, so an on-hold customer on
     a session that never reaches minimum is not silently skipped.

REASON:
  Developer Specification §6 (payment logic), §7 steps 7-9 (minimum-
  participant and teacher-assignment checks), §9 (minimum participant
  requirement), §11 (replacement session) — all of these implicitly
  assume a reserved booking counts toward these checks regardless of

CHANGE:
  Fixed the two additional booking edge cases from the client's latest
  pre-acceptance review email:

  1. Duplicate session IDs. validate_add_to_cart() computed the
     required-count check ($count = count($selected)) BEFORE
     deduplicating the submitted session IDs — array_unique() ran only
     afterward, purely to build the validation/reservation loop's own
     list. A request selecting the same session twice for a package
     that requires an exact number of sessions (e.g. two entries with
     id=5 plus two more distinct IDs, for a 4-session pack) therefore
     passed the count check (4 == 4) even though only 3 distinct
     sessions were actually chosen. Fixed by moving the
     array_column()/array_map()/array_unique() dedup to run first, and
     computing $count from the deduped list — a duplicate-containing
     submission is now correctly rejected, naming the real unique count
     ("you selected 3 unique session(s)") rather than the raw one.

  2. Partial reservation with no rollback. add_cart_item_data()
     reserved each session in the loop one at a time via
     WPES_Bookings::reserve(); if one call returned a WP_Error (its
     capacity disappeared between validate_add_to_cart()'s check and
     this actual reservation — a real timing gap, not just a
     theoretical one), the code silently skipped it and kept going,
     leaving every session reserved *before* the failure still booked.
     The customer would end up with a partially reserved package and no
     error. Fixed to be all-or-nothing: on any WP_Error, every booking
     ID already reserved in that same attempt is passed to
     WPES_Bookings::cancel(), then a plain PHP Exception is thrown with
     the gateway-style error message. This is not a custom abort
     mechanism — verified directly against WooCommerce core's own
     class-wc-cart.php (pulled from staging via FTP): WC_Cart::
     add_to_cart() wraps its entire body, including the
     woocommerce_add_cart_item_data filter call this function is
     hooked to, in a try/catch(Exception), converting a thrown
     Exception into a clean wc_add_notice() error and adding nothing to
     the cart. So this reuses WooCommerce's own established extension
     contract for "reject this add-to-cart," rather than inventing one.
