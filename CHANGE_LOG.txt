CHANGE:
  Added the Teacher data model and a full admin management screen.
  Specifically:
  - New DB tables: wpes_teachers (name, email, status) and
    wpes_teacher_classes (many-to-many: which classes/subjects a
    teacher is suitable to teach). Bumped DB_VERSION 1.4.0 -> 1.5.0
    and WPES_VERSION to match (per AGENTS.md schema-change rule).
  - New columns on wpes_sessions: assigned_teacher_id (nullable FK)
    and teacher_assigned_at (audit timestamp).
  - New class WPES_Teachers: CRUD, class-assignment, and
    get_teachers_for_class() (the lookup future invite logic will
    use to find "suitable teachers" for a session).
  - New admin submenu "Teachers" (list, add/edit modal with a
    class/subject checklist, archive, delete) — mirrors the
    existing Classes screen's UI pattern exactly.
  - Sessions admin screen: added a "Teacher" column and an
    assigned-teacher dropdown in the Edit Session modal (dropdown
    is populated per-class via a new AJAX endpoint, since only
    teachers linked to that session's class are valid choices).
    This is a manual admin control only in this pass — no
    automatic invite/accept-link workflow yet (that is the next
    piece of work).
  - WPES_Sessions::query() (admin listing) now LEFT JOINs the
    teacher name; WPES_Sessions::update() now accepts
    assigned_teacher_id as an editable field.

REASON:
  Developer Specification section 10 ("Teacher Assignment via
  Email and Accept Link") and the client's direct instruction
  ("the complete Teacher workflow has not been implemented yet...
  implement the required Teacher functionality"). This is the
  foundation everything else in the spec (minimum-participant
  confirmation, automatic invites, payment capture trigger) will
  attach to, so it went first. No existing functionality was
  changed in behavior — only additive: new tables, new columns
  (nullable, default unassigned), new admin screen, new optional
  form field. Existing booking/checkout/payment flow untouched.

CHANGE:
  Automatic teacher invitation via Accept-Link, and minimum-
  participant tracking, wired on top of last session's manual
  Teacher admin screen. Specifically:
  - New DB_VERSION 1.5.0 -> 1.6.0: new table wpes_teacher_invites
    (one row per teacher invited to a session; status pending /
    accepted / expired / superseded); new column
    wpes_sessions.confirmation_state (pending / confirmed),
    tracking whether a session has actually locked in (minimum
    reached + teacher assigned), independent of payment status.
  - New class WPES_Teacher_Invites: maybe_invite_teachers()
    (re-checks a session's confirmed headcount against the
    min-participants setting and, if reached with no teacher yet
    and no invite round already in flight, emails every suitable
    teacher a unique Accept-Link); handle_accept() (validates the
    token, then claims the session with a single conditional
    UPDATE ... WHERE assigned_teacher_id IS NULL — the same
    race-condition-safe discipline as WPES_Bookings::reserve(),
    just via a compare-and-set instead of a row lock, since there
    is only one column to arbitrate); sweep_expired_invites()
    (expires stale invites, emails the admin if a session's whole
    invite round lapsed with nobody assigned); run_final_checks()
    (safety-net re-check on sessions nearing their start time).
  - New public endpoint: ?wpes_teacher_accept=<token> (no login
    required, same pattern as the existing customer magic-login
    link) — shows Accepted / Already Assigned / Expired.
  - Global Settings: added Minimum Participants (default 5),
    Automatic Teacher Assignment (on/off), Teacher Invitation
    Validity (default 4h), Final Check Before Session (default
    24h) to the existing Settings screen — no new settings page.
  - Wired the trigger into WPES_WooCommerce::confirm_bookings_
    for_order() (fires after each paid booking confirms) AND into
    WPES_Admin::ajax_manual_enroll() (the existing manual-
    enrollment admin action was confirming bookings directly
    without ever re-checking the minimum — fixed so both paths
    behave consistently).
  - 3 new emails via WPES_Emailer: send_teacher_invite(),
    send_session_confirmed_to_attendees() (distinct from the
    original order-confirmation email, since a session can lock
    in well after purchase), send_admin_no_teacher_response().
  - Reused the two existing cron schedules (five-minute /
    twelve-hour) for the new sweep and final-check jobs rather
    than adding new intervals.

REASON:
  Developer Specification sections 7-11 (required booking
  workflow steps 8-10 and 14; minimum participant requirement;
  teacher assignment via email and Accept-Link) and Acceptance
  Criteria's race-condition and Accept-Link requirements.

CHANGE:
  Package payment capture (§6) plugin-side code, and the full
  Replacement Session / credit flow (§11) — the two pieces that
  were flagged as entirely unbuilt in the last progress review.

  Payment (WPES_Payments, new):
  - maybe_capture_package_payment( $order, $session_id ) — the
    single trigger point. Deliberately calls no gateway-specific
    API: it only transitions the WooCommerce order to 'completed'
    when (and only when) that order is currently 'on-hold' and not
    already captured. This is not a guess — I pulled the actual
    installed WooPayments plugin source from staging via FTP and
    confirmed directly in its code that it binds its own capture
    logic (capture_authorization_on_order_status_change) to the
    core `woocommerce_order_status_completed` hook, and that its
    "Capture charge" admin button is just the standard WooCommerce
    order-action hook `woocommerce_order_action_capture_charge`.
    Using the order's own status lifecycle rather than either of
    those directly keeps this genuinely gateway-agnostic, matching
    the spec's explicit "no custom payment system" requirement.
  - IMPORTANT — this code is currently INERT. It guards on the
    order status being 'on-hold', which never happens until
    WooPayments' "manual capture" setting is turned on (currently
    OFF on staging — confirmed via the WooCommerce REST API). That
    is a gateway-level configuration change, not plugin code, and
    the developer/AI-assistant paused on making it without the
    client's explicit go-ahead, consistent with "contact us before
    changes involving payments." Nothing else in this entry depends
    on it being on.
  - Verified while investigating: WooPayments' own settings screen
    states the authorization must be captured within 7 days or it
    is automatically cancelled. This is the concrete answer to the
    spec's own requirement to verify the gateway's supported
    pre-authorization period — worth the client/dev team confirming
    packages realistically fill within that window.

  Replacement Session (WPES_Replacements, new):
  - New table wpes_replacement_credits (one row per credit: source
    booking/session, customer, status, and where it was redeemed).
  - process_session_failure( $session ) — called from the existing
    final-check cron once a session is confirmed to still be below
    minimum this close to starting: cancels the session, cancels
    every confirmed booking on it, issues one credit per booking,
    emails each affected customer.
  - redeem_credit() — reuses the exact same WPES_Bookings::reserve()
    + confirm() path a paying customer goes through (so capacity
    and race-safety come for free), just without a checkout, so no
    additional charge is ever created.
  - My Account (My Sessions) now shows any available replacement
    credit with a session dropdown and a plain-POST "Confirm
    Replacement Session" button (admin-post.php, nonce-protected,
    no new JS) — redeeming redirects back with a plain-language
    success/failure notice.
  - WPES_Teacher_Invites::run_final_checks() now actually acts on
    the failure case instead of only ever re-inviting — this closes
    the gap flagged in the last progress review, where a session
    that never reached its minimum just sat there indefinitely.

  Also refactored the "session just confirmed" side effects
  (confirmation email, auto meeting-link send, and now payment
  capture) out of handle_accept() into a shared
  finalize_session_confirmation(), and wired the same call into the
  manual admin-assignment path (WPES_Admin::ajax_update_session) —
  previously an admin manually assigning a teacher got NONE of
  those side effects, only the automatic Accept-Link path did.
  Fixed for consistency; only fires on a genuine new assignment,
  not on every session re-save.

REASON:
  Developer Specification §6 (Payment Logic), §7 steps 3/12/13,
  §11 (Replacement Session), §14 acceptance criteria's payment and
  replacement bullets, and the Overview PDF's red path (Minimum
  NOT Reached -> Replacement Session).
